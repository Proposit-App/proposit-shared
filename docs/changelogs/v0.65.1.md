## Fixed

**`parseResponse` threw on the typed 404 that means "no review yet", blocking a
signed-in reader's first review.**
`GET /api/v1/argument/{id}/{v}/reviews` answers with `{ "error": "not_found" }`
at status 404 (`ReviewGetNotFoundResponse`, declared in this package and emitted
by the server's reviews route). That body matches neither `ReviewGetResponse`
nor the standard `{ errorMessage, errorID, statusCode }` shape, so `Value.Parse`
threw, `getMyReview` rejected, and mobile's `loadReview` never settled.

Fixed **in the normalizer**, not at the call site: `parseResponse` already
auto-detects the `GRAMMAR_VIOLATIONS` 422 and `MUTATION_CONFLICT` 409 envelopes,
and this extends that mechanism rather than adding a parallel one. A
`try`/`catch` or a widened schema per call site is what lets the next coded
envelope reintroduce the same defect, and this is the third time it has been
reintroduced.

The four detections now read as one `??` chain over a small
`coded(status, envelope)` helper, so the part of each block that was identical
is written once and the next envelope is one line. The default-form-only gate is
unchanged: a caller passing an explicit error schema keeps the pre-0.11
single-schema behaviour.

**Two more coded 4xx envelopes were failing the same way**, found by auditing
the rest of `src/api-client/**` as part of this fix.

`{ error: "already_exists", reviewId }` at 409 from `POST …/reviews`
(`ReviewCreateConflictResponse`), reached from a second tab or a retry after a
partial failure. `createReviewRemote` threw instead of returning it, so the
`reviewId` needed to adopt the existing review never arrived.

`{ code: "TOKEN_BUDGET_EXCEEDED", message, usage }` at 402
(`BudgetExceededErrorBodySchema`), emitted by every LLM-bearing entry route and
reachable through `importArgumentImpl` and `buildArgumentImpl`. The schema
shipped here but nothing detected it, so the usage figures a client shows the
user were unreachable.

**New guards**, mirroring `isGrammarViolationsError` / `isMutationConflictError`
and exported from `@proposit/shared/api-client`: `isReviewNotFoundError`,
`isReviewAlreadyExistsError`, `isBudgetExceededError`. They are needed rather
than decorative — the error half of a `parseResponse` result is a union whose
`ErrorResponseSchema` member has no `error` key, so a bare
`res.error.error === "not_found"` does not typecheck.

**Regression tests** drive real `Response` objects through `getMyReviewImpl`,
`getReviewByIdRemoteImpl` and `createReviewRemoteImpl`, asserting they resolve.
A schema-level test would not have caught any of this: every one of these
envelopes already had a correct schema, and the defect was in the normalizer
that never consulted it.

## Note for the server

`{ error: "not_found" }` at 404 is, arguably, the underlying mistake: a reader
having no review yet is an ordinary empty state, and `200 { review: null }`
would model it without every client needing to know that one 404 is not a
failure. The contract is the server's and the web app depends on it, so nothing
is changed from here — raised for routing, not acted on.
