# v0.15.0 changelog

`v0.15.0` lands the `@proposit/shared` half of the ingestion-pipeline
retry initiative (Pipeline Refinement, Area 2 — slice S-shared), on
the `pipeline-refinement/retry-schemas` branch.

Minor release — additive only, no breaking changes. Lands the
wire-contract surface (`RetryTaskResponse` + two api-client methods)
that `proposit-server`'s retry routes (slice S2) consume.

## Schemas — new task-retry response sub-entry

- **Add:** `src/schemas/api/task-retry/index.ts`. Single-file
  response-only schema module. Exports `RetryTaskResponse` — an alias
  of the existing `ArgumentCreateTask` schema (`src/schemas/tasks.ts`)
  — and its derived `TRetryTaskResponse` type. Both retry routes
  (whole-task and per-stage) produce the same artifact: a fresh
  `argument_create` task whose `previousId` points at the failed task.
  **Zero change to `tasks.ts`** — `ArgumentCreateTask` was already
  individually exported, and `BaseTaskSchema.previousId` already models
  retry lineage.
- **Add:** `src/schemas/api/task-retry/__tests__/schema.test.ts` —
  9 TypeBox `Value.Check` / `Value.Parse` tests covering a fresh retry
  task (`previousId` set), a completed task with `resultData`, a
  first-run task (`previousId: null`), the optional nullable
  `responseId`, the wire round-trip (string dates → `Date` via
  `Convert` + `Parse`), and rejection paths (non-`argument_create`
  type, missing required field, malformed `data.argumentId`,
  non-numeric `status`).

## API-client — retry method pair

- **Add:** `src/api-client/tasks/task-retry.ts`. Two `*Impl` functions:
    - `retryTaskImpl(config, taskId)` —
      `POST /api/v1/task/[taskId]/retry`, parses against
      `RetryTaskResponse`.
    - `retryStageImpl(config, taskId, stageRowId)` —
      `POST /api/v1/task/[taskId]/pipeline/stages/[stageRowId]/retry`,
      parses against `RetryTaskResponse`. `stageRowId` is
      attribution/logging only — execution is a whole-task re-run
      regardless.
      Both are **path-params-only POSTs** (no request body) and use the
      no-body `parseResponse` pattern (mirroring `deleteReactionImpl`),
      not `strictFetch`. Path params are percent-encoded via
      `encodeURIComponent`. `TApiClientConfig` is imported from
      `../config.js`.
- **Modify:** `src/api-client/factory.ts`. Two new keys registered in
  the `impls` registry: `retryTask` and `retryStage`. The mapped-type
  `TApiClient` derives both new method signatures automatically — no
  manual type wiring.
- **Add:** `src/api-client/tasks/__tests__/task-retry.test.ts` —
  5 mock-fetch tests: URL shape + POST method + no-body assertion for
  both endpoints, response parse (with `EncodableDate` → `Date`
  decoding), percent-encoding of `taskId` (and of both `taskId` +
  `stageRowId` for the stage route), and a 409 path that surfaces as a
  parsed error reply (`result.ok === false`).

## Package.json exports

- **Modify:** `package.json`. New sub-entry export for
  `./schemas/api/task-retry`, slotted alphabetically between
  `./schemas/api/review` and `./schemas/api/user`. All three conditions
  (`types`, `import`, `default`) populated per shared's CLAUDE.md design
  rule. No peer-dep range change.
