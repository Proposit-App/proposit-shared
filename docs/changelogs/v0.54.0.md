# Changelog — v0.54.0

<changes starting-hash="ad6ae53" ending-hash="4351f3e">

## Fixed

- **`buildOperatorQueue` no longer leaks derivation premises into the review
  operator queue** (`src/engine/review/step-queue.ts:53`). It did not filter on
  `premise.type`. A citation-populated derivation premise is
  `IMPLIES(citation_var, Q)` — an inference, so `listSupportingPremises()`
  returned it, carrying a decidable operator, so the second gate passed. It then
  rendered to the user as "Premise N (Supporting)". Naked-Q derivation premises
  self-excluded only incidentally, having no operator expressions.

    Measured across 297 argument-versions, the review count exceeded the argument
    header's on 200, was lower on 51, and matched on 46. Two independent
    mechanisms, and the arithmetic closes:
    `review = header − 1 + (citation-populated derivation premises)`.

    **Only the leak is a defect and only the leak is fixed.** The constant −1 is
    not: `getDecidableOperatorExpressions()` is empty for a bare-variable premise,
    and the standard authored conclusion is a bare variable, so the conclusion can
    never enter the queue — manufacturing a step for it would be a review prompt
    with no operator to decide. `TReviewProgress.totalPremises` is the length of
    this queue, NOT a premise count; `step-queue.ts:19-42` now states that contract
    in a doc comment. Consumers must not label it as a premise count.

- **The snapshot premise schema stopped declaring `derivedClaimId`, so every
  derivation premise lost it crossing the API** (`src/schemas/snapshot.ts`).
  `Type.Omit` over `PropositionalPremiseSchema` flattens the
  `freeform | derivation` union it intersects, keeping only the properties both
  members share — and `derivedClaimId` lives on the derivation member alone. The
  same hazard is already called out for variables at the top of that file, which
  omits each union member separately; the premise case hid because its union sits
  inside an `Intersect`.

    Latent until this release. A schema that does not declare a property still
    _validates_ a value carrying it, so the snapshot checked fine on the way out.
    What changed is that `Value.Encode` now runs a real pipeline —
    `EncodableDate` became a `Codec` in core 3.3.0, where `Type.Base` took no part
    in the encode pass — and Encode projects onto the declared shape. The field
    was stripped, then failed `CorePremiseSchema` (which requires it) during
    `fromServerData`'s rollback, so `proposit-server`'s argument view answered
    **500 for any argument with a citation-backed claim**.

    Caught by consumer e2e; no unit test encoded a snapshot, and validation alone
    cannot see it. Pinned by `src/schemas/__tests__/snapshot-derivation-premise.test.ts`,
    which asserts through an encode rather than a check.

- **`parseRequest`/`parseResponse` assert before decoding.** `Value.Decode`
  applies each schema's `default` before it validates, so moving off
  `Value.Parse` (below) silently redefined a valid body: a request with a
  required key omitted stopped being an error and started being populated from
  the schema default. Caught by `proposit-server`, where
  `POST /api/v1/user/invite` with `presetSystemRole` omitted returned 200 and
  minted an invitation row with the defaulted role, having previously returned
  400 with no row. Every request schema carrying a defaulted field was affected
  identically. `Value.Assert` now runs first, restoring the pre-migration
  contract while keeping the decode pass that rehydrates `EncodableDate`.

## Changed

- **`EncodableDate` migrated off the removed `Type.Base`**
  (`src/schemas/common.ts`). typebox 1.3.x deleted `Type.Base`, so
  `export class TDateType extends Type.Base` threw
  `TypeError: Class extends value undefined is not a constructor or null` at
  module-evaluation time. The declared `^1.1.14` admitted 1.3.x, so a consumer
  bump alone reached it. `typebox` is now `^1.3.8`.

    The shape is
    `Type.Codec(Type.Refine(Type.Unsafe<Date>({}), isDate, …)).Decode(toDate).Encode(identity)`
    — identical to core's independently-defined copy. The definition stays local
    rather than importing core's, per the existing cross-copy identity constraint:
    TypeBox resolves a type's identity structurally against the copy of the library
    that built it. Both packages resolve one hoisted typebox in the consumer, so a
    split resolution would leave whichever guessed wrong broken.

    `Value.Convert` + `Value.Parse` became `Value.Decode` at
    `src/utils/utils.ts:82-84,170-176` (`parseRequest`/`parseResponse`) and
    `src/engine/review/review-store.ts:132-134`.

    `Check` now also accepts a serialized date string. Forced, not chosen:
    `Value.Decode` asserts before running decode callbacks, and union member
    selection skips members failing `Check`, so a strict `instanceof Date`
    refinement made `Nullable(EncodableDate)` unresolvable for any wire value.
    Numbers remain rejected.

- **Stored free-text fields carry `maxLength` at the write boundary.** New
  `MutableClaimWriteFieldsSchema` (`src/schemas/model/claims.ts:61-90`) used by
  the create + update bodies; `MutableArgumentFieldsSchema`
  (`src/schemas/model/arguments.ts:23-41`) was already write-only. Caps reuse the
  constants the server already enforced imperatively —
  `ARGUMENT_TITLE_MAX_LEN` 100, `ARGUMENT_DESCRIPTION_MAX_LEN` 500,
  `CLAIM_TITLE_MAX_LEN` 100, `CLAIM_BODY_MAX_LEN` 500 — so nothing previously
  accepted is now rejected. Moderation `note` was genuinely uncapped and takes a
  new `MODERATION_NOTE_MAX_LEN` 5_000 (`src/consts/moderation.ts`).

    **Deliberately write-side only.** `MutableClaimFieldsSchema` composes into
    `NormalClaimSchema` → `ClaimSchema`, which `strictFetch`/`parseResponse`
    validates on every _response_; capping in place would reject an already-stored
    over-length row on the way out.

## Added

- **`destructiveAsText` colour token** (`src/ui/colors.ts`), `#a75041` light /
  `#c87263` dark. The clay fill measures 4.45 / 4.91 / 4.23 (light) and
