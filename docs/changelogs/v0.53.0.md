# Changelog — v0.53.0 (`79493f5..85efed1`)

## Added

- `apiClient.deactivateAccount()` (`src/api-client/user/deactivate-account.ts`,
  registered on the factory). Issues `PATCH /api/v1/user/me` and returns the
  updated user. Takes **no argument**: the route accepts exactly one state, so
  there is nothing for a caller to choose, and a client that could pass a state
  would hand every authenticated caller a moderator's reach.
- `DeactivateAccountRequest` (`src/schemas/api/user/index.ts`) — a single
  `Type.Literal(AccountStates.DEACTIVATED)` rather than the `AccountStates`
  union, so an attempt to ask for `banned` or `deleted` is a compile error rather
  than a server-side 400.

v0.52.0 introduced `accountState` but no way to set it; this is what lets a
consumer act on it.

## Removed

- **`UserSchema.deleted`** (`src/schemas/model/users.ts`) — **breaking**, and the
  reason this is a minor rather than a patch.

    The boolean was the third place account state used to live, alongside the
    `BANNED` / `DEACTIVATED` values v0.52.0 took out of `tier`. `accountState` now
    carries `DELETED`, so the flag was redundant; it survived v0.52.0 only because
    the server dual-wrote it through a rolling deploy.

    It had to go before `proposit-server` could drop the underlying column: the
    field was **required**, so the server's `createResponse` validation failed on
    every route returning a user the moment the column disappeared. The two are one
    change split across two repos.

    Nothing read it. A sweep of `proposit-server` and `proposit-mobile` found no
    `.deleted` access on a user object outside test fixtures and the server's own
    dual-write. Consumers reading account state should use `accountState`, which
    distinguishes `deleted` from `banned` and `deactivated` rather than collapsing
    them into one boolean.

## Tooling

- `pnpm run pack:branch` (`scripts/pack-branch.sh`) names a consumer-validation
  tarball after the branch it was built from —
  `proposit-shared-<version>-<branch>.tgz`. Plain `pnpm pack` names by version
  alone, so two branches at the same version write the same filename to the same
  directory and a consumer pinned to it installs whichever packed last —
  silently, because the version string still matches whatever the consumer
  checks. Git worktrees make that routine rather than rare. The script also
  removes its own previous output, since a stray `*.tgz` in the package root
  makes `pnpm publish` fail with an EUSAGE "two package-specs" error.
