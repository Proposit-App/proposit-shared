# 0.7.1 release notes

Patch release. Adds an `existingConsequentVariableId` parameter to `mutateCreateDerivationPremise` so callers can adopt an already-existing claim-bound variable as the derivation consequent rather than letting the engine allocate a duplicate. Resolves a DB-level unique-constraint collision that the server's heal-on-write path was hitting on legacy / fork-from-older-argument claims. Background: `docs/change-requests/2026-05-11-adopt-existing-consequent-variable.md`.

The addition is fully backwards-compatible at the call-site level: `consequentVariableId` becomes optional and is joined by a new optional `existingConsequentVariableId`, but existing call sites that pass `consequentVariableId` continue to work identically.

## What was wrong

`mutateCreateDerivationPremise` always emitted a brand-new claim-bound consequent variable for the derived claim. The engine's auto-allocator picks a fresh UUID and the symbol of the matching claim title; when a claim-bound variable for the same claim already lived in the argument (legacy pre-wave-2 rows that the migration never backfilled, or fork-from-older-argument flows), persisting the resulting changeset violated the DB constraint `(symbol, argumentId, argumentVersion)`.

The only callers today — `addClaim` and the server's heal-on-write path inside `addClaimCitation` — worked around the constraint by ensuring the claim was brand-new, but that workaround did not generalize. Legacy claims with a free claim-bound variable but no derivation premise hit the collision the moment the server tried to heal-on-write.

## What changed

`mutateCreateDerivationPremise` (in `src/engine/mutations/premises.ts`):

- Signature gains an optional `existingConsequentVariableId: string`. `consequentVariableId` is now also optional. Exactly one of the two must be supplied — both / neither throws a descriptive `Error`.
- **Mint mode** (`consequentVariableId` supplied): behavior unchanged from `0.7.0`. The auto-created consequent variable is removed and replaced with a caller-minted claim-bound variable using the auto var's symbol and claim version.
- **Adopt mode** (`existingConsequentVariableId` supplied): validates that the named variable is in the engine, is claim-bound, and has `claimId === data.derivedClaimId` — throws a typed error message otherwise. Then leans on core's `ensureClaimBoundVariable` reuse semantics: `engine.createPremiseWithId({ type: "derivation", derivedClaimId })` already surfaces the existing claim-bound variable as the auto consequent when one is in scope, so the implementation only needs to swap the auto naked-Q expression for one with the caller-supplied id; the existing variable is retained as-is. The merged changeset's `variables.added` does **not** contain a new claim-bound variable for `derivedClaimId`.

## Migration impact

- **`proposit-server`** — Once the dependency is bumped to `^0.7.1`, the heal-on-write path inside `addClaimCitation` can:
    - Inspect the engine snapshot for an existing claim-bound variable bound to the citing claim id.
    - If found, call `mutateCreateDerivationPremise(engine, premiseId, { …, existingConsequentVariableId: existingVar.id, consequentExpressionId })` — omitting `consequentVariableId`.
    - Otherwise call the existing mint-path variant (no change from current code).
    - Drop the typed `ClaimNeedsDerivationRepairError` / HTTP 422 stopgap that detected the collision case before the upstream fix was available, and add a model test that exercises the heal-on-write happy path for a legacy claim.
- **`proposit-mobile`** — No source change required beyond the dependency bump. Mobile does not call `mutateCreateDerivationPremise` directly today.

## Validation rules

`mutateCreateDerivationPremise` throws an `Error` (not `InvariantViolationError` — these are caller-misuse conditions, not engine-invariant violations) when:

- Both `consequentVariableId` and `existingConsequentVariableId` are supplied (`"mutually exclusive"`).
- Neither is supplied (`"must supply exactly one"`).
- `existingConsequentVariableId` does not resolve to any variable in the engine (`"not found in engine"`).
- The named variable exists but is not claim-bound (`"not claim-bound"`).
- The named variable is claim-bound to a different claim than `derivedClaimId` (`"is bound to claim X, expected derivedClaimId Y"`).
