# v0.9.0 release notes

`v0.9.0` is the grammar-tiers minor of `@proposit/shared` — the second slice of the cross-repo Grammar Tiers initiative (spec at `proposit-orchestration/docs/superpowers/specs/2026-05-13-grammar-tiers-design.md`).

## Peer dep bump: `@proposit/proposit-core@^1.0.0` (breaking)

Shared's `peerDependencies['@proposit/proposit-core']` range moves from `^0.12.3` to `^1.0.0`. Consumers must bump core in lockstep when picking up shared `0.9.0`. The full migration mapping for the engine-wrapper surface (`PremiseEngine` / `ArgumentEngine` API changes, the `grammarConfig` → `behavior` model, MDPE deletion, the `validate(tier)` four-tier API, the `populateFromCitations` / `populateFromAxioms` split) is in core's own `v1.0.0` release notes. Shared `0.9.0` adapts to that surface; it doesn't itself add new wire-format types — those live in core now.

## `./schemas/grammar` — re-export of the four-tier grammar wire format

Adds a new exports-map entry `./schemas/grammar` that **re-exports** the wire-format schemas + types from `@proposit/proposit-core`:

- `GrammarTierSchema` / `TGrammarTier` — the four tiers (`structural` ⊇ `evaluable` ⊇ `derivable` ⊇ `presentable`).
- `GrammarRuleCodeSchema` / `TGrammarRuleCode` — canonical rule-code union (S-1..S-14, E-1, E-3..E-7, D-1..D-6, P-1..P-5; codes `E-2` and `D-7` are reserved).
- `ViolationSchema` / `TViolation` — the per-violation envelope returned by core's `validate(tier)` and surfaced inline by server/mobile UIs. Allows additional properties so rule-specific context fields can be attached without a wire-format break.

The 2026-05-14 cross-repo design restructure relocated wire-format ownership from shared to core, matching the existing dep direction (shared has core as a peer dep). Server and mobile keep their existing `import { TViolation, ... } from "@proposit/shared/schemas/grammar"` paths via the re-export; they may also import the types directly from `@proposit/proposit-core` — both paths resolve to the same TypeBox objects via the dep range.

## `./schemas/api/grammar-violations` — 422 envelope

Adds `GrammarViolationsResponseSchema` / `TGrammarViolationsResponse` — the standardized response server endpoints return when submit/publish requests fail a grammar-tier gate. Discriminated by `error: "GRAMMAR_VIOLATIONS"` so clients can switch on response type without sniffing tier/codes. The envelope composes `TViolation` (imported through the new re-export module); mobile consumes this same schema to render violations inline.

## Engine-wrapper refactor against core 1.0

The bulk of `0.9.0` is the engine-wrapper refactor that core 1.0's surface changes forced. The wrappers under `src/engine/` were consuming pre-1.0 APIs that have been removed or restructured:

- **`src/engine/engine.ts` (`PropositArgumentEngine`):** drops the `TGrammarConfig` import + the `RUNTIME_GRAMMAR` / `LOADING_GRAMMAR` constants + the per-engine `grammarConfig` constructor option, replacing them with core 1.0's single `behavior: 'assistive' | 'permissive'` setting (default `'assistive'`). The reactive-snapshot invariant sweep moves from `this.validate()` (the pre-1.0 method returning `{ ok, violations }`, now split in 1.0) to `this.validateInvariants()` which preserves the legacy semantics. `fromServerData` drops the per-premise expression-config rewrite to `LOADING_GRAMMAR` and the post-rollback `pe.setGrammarConfig(RUNTIME_GRAMMAR)` re-tightening loop — core 1.0's `rollback` / `fromSnapshot` / `fromData` accept any Structural-valid snapshot regardless of higher-tier state, so the per-premise dance becomes unnecessary.
- **`src/engine/derivation.ts`:** drops the re-exports of `ManagedDerivationPremiseEngine` (deleted in core 1.0's D1), `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION` (deleted in D4 — broken-tree derivation premises continue to surface as the unchanged `DERIVATION_STRUCTURE_INVALID`), `DERIVATION_ANTECEDENT_NON_EMPTY` (gone — `populateFromCitations` / `populateFromAxioms` return `{ kind: 'no-op' }` on already-populated premises rather than throwing), and `TVariableMaterializer` (MDPE-only interface). Adds re-exports for `CREATE_DERIVATION_REQUIRES_DERIVED_CLAIM_ID` and `CREATE_DERIVATION_CLAIM_NOT_FOUND` which survived as engine-error codes.
- **`src/engine/optimistic/verification.ts`:** drops the `grammarConfig` option from the temporary `serverEngine` used for checksum comparison.
- **`src/engine/review/review-engine.ts`:** the stale-claim-assignment sweep switches from `this.argEngine.getClaim(id)` to `this.argEngine.getProjectClaim(id)` — see the rename below.
- **`src/schemas/review.ts`:** `TCoreValidationCodeSchema` swaps the 18th literal from `DERIVATION_STRUCTURE_INVALID_AT_EVALUATION` to `DERIVATION_STRUCTURE_INVALID` to match core 1.0's runtime emitter.

### Renamed: `getClaim` → `getProjectClaim` (breaking for direct callers)

Core 1.0 promoted `getClaim(claimId, claimVersion)` to the `ArgumentEngine` base surface, returning the minimal `TCoreClaim` `{ id, version, type, frozen, checksum }` shape used by claim-bound-variable validation. Shared's existing domain method `getClaim(id)` returned the much richer `TClaim` (a discriminated union over normal / citation / axiomatic with `createdOn`, `creatorId`, `title`, etc.) drawn from the per-engine `claimsMap`. Those two return types are incompatible, so they can't coexist as overload + override on the same method name.

Shared's domain accessor is renamed to **`getProjectClaim(id)`** (matching the existing `getProjectSnapshot` naming convention). Both methods are now available on `PropositArgumentEngine`:

- `engine.getClaim(claimId, claimVersion)` — inherited from core; returns the minimal `TCoreClaim` for engine-internal use.
- `engine.getProjectClaim(id)` — shared's domain method; returns the rich `TClaim` from the per-engine `claimsMap`.

Server's `claim-actions.ts` callsite (`engineRef.current.getClaim(claimId)`) needs to update to `getProjectClaim` when bumping shared to `0.9.0`. Mobile has no callsites.

### Behavior change: `populateDerivationFromCitations` for n ≥ 2

The legacy helper at `src/engine/mutations/premises.ts:493` is still exported with strengthened `@deprecated` JSDoc directing consumers at core 1.0's native `engine.populateFromCitations(claimId, lookup)` and `engine.populateFromAxioms(claimId, lookup)`. Two scope-decision points:

- **Kept (not deleted).** The briefing offered (a) delete or (b) deprecate. Chose (b) because the helper's IMPLIES/OR tree construction uses the unchanged `wrapExpression`/`appendExpression` mutation surface and continues to function against core 1.0, and because deleting would force server's single callsite to migrate in the same change cycle as the peer bump while also deleting a substantial test suite. Target removal: shared `^1.0.0`.
- **Output shape changed for n ≥ 2** (this is the behavior change). Pre-1.0 the helper produced the canonical formula-buffered `IMPLIES(formula(OR(c1, …, cn)), Q)` tree, relying on the engine's pre-1.0 `wrapInsertFormula` auto-rule to slip the formula in during the `wrapExpression` call itself (the buffer landed inside the captured changeset on the same mutation surface). Core 1.0 ran the AN rule set asynchronously after each mutation in `assistive` behavior, and AN-3 (delete 0-child operators/formulas) would have destroyed the transient 0-child OR between the wrap and the children-append. The helper now flips the engine to `'permissive'` for the duration of the n ≥ 2 build (`engine.setBehavior('permissive')` → wrap + per-citation appends → `engine.setBehavior(priorBehavior)`), which suppresses AN throughout the build and emits the unbuffered `IMPLIES(OR(c1, …, cn), Q)` tree. The unbuffered shape is Structural-valid in core 1.0 — only P-1 (Presentable rule) complains.

Consumers that need the canonical formula-buffered shape run `engine.normalize()` after the helper returns. The additional state changes from `normalize()` are NOT captured in the helper's returned changeset; callers using the changeset for persistence either accept the unbuffered shape at storage and materialize the buffer on read, snapshot-diff to capture the normalize-driven changes, or migrate to `engine.populateFromCitations` whose return shape (`{ kind: 'no-op' | 'populated', state }`) integrates with the four-tier model.

Server has **two production callsites** for `populateDerivationFromCitations` that need to choose one of these options when picking up shared `0.9.0`:

- `proposit-server/src/model/claim.ts:600`
- `proposit-server/src/app/api/v1/argument/[argumentId]/[version]/citations/[edgeId]/route.ts:115`

Mobile has no callsites.

## Pre-restructure schemas removed

The 14 pre-pivot commits on this branch (before the 2026-05-14 design restructure) authored `TGrammarTier` / `TGrammarRuleCode` / `TViolation` schemas locally at `src/schemas/grammar/{tier,rule-code,violation}.ts`. Those files are deleted in `0.9.0`; their contents are now canonical in core's `src/lib/grammar/types.ts` and surface in shared via the re-export at `src/schemas/grammar/index.ts`. The 422 response envelope at `src/schemas/api/grammar-violations.ts` re-points its imports to the re-export module; runtime shape is unchanged.

## Docs

`CLAUDE.md` "Grammar rule-code coordination protocol" section is rewritten from the pre-pivot **shared → core → consumers** order (which would have been correct under the original wire-format-in-shared design) to the post-pivot **core → shared → consumers** order matching the actual ownership pivot. The dep range + core's exhaustive union types remain the TypeScript-level enforcement point.

## Versioning intent

Pre-1.0 minor bump (`0.8.0` → `0.9.0`) per the policy in `CLAUDE.md`. The peer-dep range expansion and the engine-wrapper API rewrite are the breaking-behavior drivers under the pre-1.0 minor-may-break rule; consumers MUST bump `@proposit/proposit-core` to `^1.0.0` in the same change cycle when picking up shared `0.9.0`.
