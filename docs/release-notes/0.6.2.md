# Release notes — v0.6.2

Patch release. Fixes a `mergeChangesets` invariant violation in `clearDerivationAntecedent` that fires whenever the mutation runs against an engine reconstructed via `rollback(snapshot)` — i.e. every request in `proposit-server`'s wave-2 `addClaimCitation` flow once the citing claim already has at least one citation. Background: `docs/change-requests/2026-05-08-clear-derivation-modified-removed-conflict.md`.

## Why this is patch (and not minor)

Pure bug fix. No public API surface change, no signature change, no behavior change for valid inputs that previously succeeded — only a previously-throwing call now returns the changeset it was always supposed to.

## What was wrong

`clearDerivationAntecedent` builds its changeset from three sub-mutations:

1. `pm.removeExpression(antecedent.id, true)` — cascade-removes the antecedent. On a reloaded engine the parent `IMPLIES` node's descendant-checksum is recomputed and `IMPLIES` is emitted as `modified`. (On a fresh in-process engine, the descendant-checksum tracker is in a different state and `IMPLIES` is not emitted as `modified`, which is why this never fired in the existing in-process tests.)
2. `pm.removeExpression(rootExprId, false)` (under `PERMISSIVE_GRAMMAR_CONFIG`) — removes `IMPLIES`, promoting the consequent variable to root. `IMPLIES` lands in `removed`.
3. `engine.removeVariable(varId)` for each citation-bound variable.

The internal `mergeChangesetSequence` helper sanitized `added` vs `modified` collisions across sub-changesets, but not `modified` vs `removed`. So step 1's `modified IMPLIES` survived into step 2's merge alongside `removed IMPLIES`, and `mergeChangesets` correctly rejected the result on its single-bucket invariant.

## What changed

`mergeChangesetSequence` (in `src/engine/mutations/premises.ts`) now collects both `addedIds` and `removedIds` across the input sub-changesets. The per-changeset sanitization step drops `modified` entries whose ids appear in EITHER set. The resolution rule is symmetric to the existing rule for `added`: if an entity is being removed across the merged result, intermediate descendant-checksum changes on it are irrelevant to the post-merge state.

`added` + `removed` collisions are still left for `mergeChangesets` to surface — those are genuine logic errors and should be loud.

## Migration impact

- **`proposit-server`:** the `clearDerivationAntecedentSafe` workaround in `src/model/claim.ts` (post-processed `modified`/`removed` sanitization mirroring this fix) can be deleted once `@proposit/shared` is bumped to this release. Replace call sites with the shared `clearDerivationAntecedent`.
- **`proposit-mobile` / other clients:** no source change required. Calls that previously worked keep working; calls that previously threw on reloaded engines now succeed.
