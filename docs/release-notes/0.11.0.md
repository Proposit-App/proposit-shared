# v0.11.0 release notes

`v0.11.0` closes the client-side half of the Grammar Tiers initiative's
422-envelope plumbing. The single change: `parseResponse` now auto-detects
the `GRAMMAR_VIOLATIONS` envelope on HTTP 422 responses and surfaces it
as a typed branch of its discriminated return — so api-client calls under
`argument/logic/` (and any other 422-emitting endpoint) stop throwing
"Error: Parse" and start returning a structured envelope callers can
narrow on. No engine-wrapper churn, no peer-dep bump.

## Breaking (type-level) — `parseResponse` return type widens

The 2-arg (default) form of `parseResponse` at `src/utils/utils.ts` now
returns:

```ts
Promise<
    | ParsedSuccess<T>
    | ParsedError<typeof ErrorResponseSchema>
    | ParsedError<typeof GrammarViolationsResponseSchema>
>
```

Pre-0.11 the error half was a single `ParsedError<typeof ErrorResponseSchema>`.
Existing callers' **runtime code continues to work unchanged** — the
auto-detect only fires on 422-with-`GRAMMAR_VIOLATIONS`-body, and all
other failure paths still parse through `ErrorResponseSchema`. The
breakage is **type-level**: any callsite that destructures
`result.error.errorMessage` / `result.error.statusCode` directly (without
first narrowing the union) now fails to compile because those fields
exist only on the `TErrorResponse` branch.

Migration is mechanical — narrow before accessing:

```ts
const result = await apiClient.someCall()
if (!result.ok) {
    if ("errorMessage" in result.error) {
        // TErrorResponse branch: legacy fields available
        console.error(result.error.errorMessage, result.error.statusCode)
    } else {
        // TGrammarViolationsResponse branch
        result.error.violations.forEach(renderInline)
    }
}
```

Or use the `isGrammarViolationsError()` guard added in `0.10.0`:

```ts
import { isGrammarViolationsError } from "@proposit/shared/api-client"

if (!result.ok) {
    if (isGrammarViolationsError(result.error)) {
        // ...
    } else {
        // result.error is TErrorResponse here
    }
}
```

### 3-arg overload unchanged

Callers using the explicit-error-schema form
(`parseResponse(resp, SuccessSchema, MyErrorSchema)`) keep their
narrower return type and **bypass the GRAMMAR_VIOLATIONS auto-detect
entirely**. The body parses through the caller-supplied schema, same as
pre-0.11. Callers that want both — explicit schema _and_ grammar-violations
auto-detect — should compose:

```ts
parseResponse(
    resp,
    SuccessSchema,
    Type.Union([MyErrorSchema, GrammarViolationsResponseSchema])
)
```

## Fixed — `argument/logic/` 422 responses no longer crash the api-client

Pre-0.11, server endpoints under `/api/v1/argument/.../logic/...` that
rejected requests via the grammar-tier gate returned the 422-with-
`GRAMMAR_VIOLATIONS` envelope. `parseResponse` parsed the body through
`ErrorResponseSchema`, which threw "Error: Parse" because the shapes
don't align. The thrown error surfaced to callers as an opaque rejection
with no structured violation list.

`0.11.0` fixes this: the same call now returns
`{ ok: false, error: TGrammarViolationsResponse }` and callers can render
the violations inline. No api-client signature changes are needed beyond
the type narrowing described above.

## No runtime migration required

Consumers that don't currently narrow on `result.error` keep working at
runtime. The TypeScript compiler surfaces the new branch as a discriminated
union — opting into the structured envelope is just code that didn't
typecheck before.

## Versioning intent

Pre-1.0 minor bump (`0.10.0` → `0.11.0`) per the policy in `CLAUDE.md`.
The `parseResponse` return-type widening is the breaking driver under
the pre-1.0 minor-may-break rule. Peer-dep range on
`@proposit/proposit-core` stays at `^1.0.0` — no engine surface changes
in this release.
