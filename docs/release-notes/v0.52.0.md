# Release notes — v0.52.0

## An account's state is no longer its price plan

`users.tier` used to answer two unrelated questions with one number: what a user
is entitled to (`FREE`, `PREMIUM`, …) and what has happened to their account
(`BANNED`, `DEACTIVATED`). Because both lived in the same column, putting an
account into a state overwrote what it had paid for. That is survivable only
while no state can be undone — and bans are appealable. Unbanning a wrongly
banned `PREMIUM` customer would have quietly returned them as `FREE`, with
nothing left in the row to show the mistake.

So state moves onto its own axis. `@proposit/shared` now exports `AccountStates`
— `"active"`, `"deactivated"`, `"banned"`, `"deleted"` — a TypeBox schema for it,
and an `accountState` field on `UserSchema`. `UserTiers` keeps only entitlements,
and `UserTierLimits` / `UserTierNames` lose the all-zero rows that existed solely
to give the two state values something to point at. Strings rather than numbers,
because this value shows up in queries, logs, and admin payloads, where
`"banned"` is worth more than `101`.

Alongside it, `LOCKED_OUT_ACCOUNT_STATES` and `isLockedOut(accountState)` name
the states that refuse authentication: `BANNED` and `DELETED`. **`DEACTIVATED` is
not one of them**, and that omission is the point of the release. Deactivation is
meant to be a break, not an exit, and signing back in is how it ends — so sign-in
has to succeed for a deactivated account or the state becomes a trap.

## Breaking: `isPlatformDisabled` is gone

`isPlatformDisabled` and `PLATFORM_DISABLED_TIERS`, published in v0.51.0, are
removed rather than renamed. Their answer for `DEACTIVATED` was `true`, and the
new answer is `false` — so any consumer that kept compiling against the old name
would have inherited the exact behaviour this change exists to reverse, silently.
Deleting the symbols turns that into a compile error instead.

Consumers move to `isLockedOut(accountState)` and stop reading state out of
`tier`. `UserSchema.accountState` is required, so any code constructing a user
value must supply one. `NO_ASSIST` deliberately stays at `103`, gap and all —
those numbers are stored, and renumbering would re-map live accounts.
