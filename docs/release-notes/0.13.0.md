# v0.13.0 release notes

`v0.13.0` is a minor release that lands the `proposit-shared` half of
the ingestion-pipeline initiative (Phase 1, slices 1E + 1E.A + 1E.B).
Two narrow additive surfaces ship at the schema layer, plus two
behavior changes in the engine mutation surface that follow from
bumping `@proposit/proposit-core` from `^1.0.0` to `^1.1.1` (which
pulls in core's E-7 invariant from `1.0.2`).

Read the "Behavior changes" section carefully before bumping — the
engine-mutation changes are load-bearing for any consumer that
authors role transitions via `mutateUpdatePremiseRole` or creates
first premises via `mutateCreatePremise`.

## What's new

- **`@proposit/shared/schemas/ingest-argument`** — new sub-entry
  exporting `IngestionPipelineVersionSchema`
  (`"v1-single-shot" | "v2-multi-stage"`) + `IngestArgumentTaskInputSchema`
  (the internal task-input shape for the ingestion pipeline framework:
  `{ text, pipelineVersion, title?, description? }`), plus the two
  derived `T*` types. **Internal contract, not a public route schema.**
  The public route at `/api/v1/argument/import/raw_text` continues to
  accept the existing `CreateArgumentSchema` shape
  (`{ origin: "raw_text", data: { text } }`); server route handlers
  will construct `IngestArgumentTaskInput` from the public body plus
  the server-side `INGESTION_PIPELINE_VERSION` env and pass it to
  `executePipeline(...)` in `@proposit/proposit-core`.

- **`@proposit/shared/schemas/processing-failure`** — new sub-entry
  re-exporting `TProcessingFailure` from
  `@proposit/proposit-core@^1.1.1` for the ergonomic single-import
  path. **Type-only re-export for now** — core@1.1.1 ships only the
  TypeScript type, not a TypeBox runtime schema. A future shared
  minor will extend this re-export to include the runtime
  `ProcessingFailureSchema` value when core adds it. Mirrors the
  grammar wire-format re-export pattern at
  `@proposit/shared/schemas/grammar` introduced in `0.9.0`.

## Peer-dep range bump

`@proposit/proposit-core` peer range bumped from `^1.0.0` to
`^1.1.1`. Consumers must dep-bump core in lockstep with this shared
upgrade.

The bump pulls in two engine-side changes from core@1.0.2 / 1.0.3
that motivate the behavior changes below: (a) the E-7 invariant
("a non-empty argument always has a conclusion designated") makes
`engine.clearConclusionPremise()` a no-op when premises exist, and
(b) the pipeline framework surface in `@proposit/proposit-core@1.1.x`
ships `executePipeline(...)` + the `TProcessingFailure` type
referenced by the new schemas above.

## Behavior changes — engine mutations (E-7 sync)

Two helper-level changes follow from core's E-7 invariant. Both
preserve the helper layer's "engine state and `extras.role` always
agree" contract; both swap silent drift for explicit refusal or
sync-to-engine.

### `mutateUpdatePremiseRole` now throws on demote-the-conclusion

Pre-1.0.2, `engine.clearConclusionPremise()` would unset the
`conclusionPremiseId` slot, and the helper paired that with a
`syncPremiseExtrasRole(..., "supporting")` call so the demoted
premise's `extras.role` matched. Post-1.0.2 the engine refuses to
clear when premises exist — calling the helper to demote the
current conclusion in place would silently leave the engine slot
pointing at the premise while `extras.role` drifted to
`"supporting"`. Drift is exactly the gap this helper exists to
prevent.

The helper now **throws
`InvariantViolationError({ code: "ARGUMENT_NO_CONCLUSION", … })`**
when called to demote the current conclusion premise to any
other role. Both the single-premise case (no other premise to take
over) and the multi-premise case (caller hasn't picked the new
conclusion) refuse. The error's `code` is the same one core's own
`validateArgumentEvaluability` emits — server route handlers can
reuse existing pattern-matching on
`err.violations[0]?.code === "ARGUMENT_NO_CONCLUSION"` and map to
HTTP 409 Conflict.

**The legitimate way to swap the conclusion designation on a
non-empty argument is to promote a different premise** via
`mutateUpdatePremiseRole(newPremiseId, "conclusion")`. That branch
is unchanged: it atomically replaces the conclusion at the engine
slot AND demotes the prior conclusion's `extras.role` to
`"supporting"` in one shot — no two-call pattern needed.

### `mutateCreatePremise` syncs first-premise extras to `"conclusion"`

Core's `createPremiseWithId` unconditionally auto-assigns the first
premise of a new argument as conclusion (the "auto-conclusion
assignment" rule). Pre-1.0.2, the helper undid the auto-assignment
when the caller requested `role: "supporting"` by calling
`engine.clearConclusionPremise()`. Post-1.0.2 that clear is a no-op,
so the engine slot retained the auto-assigned conclusion while
`extras.role` reflected the caller's `"supporting"` — drift again.

The helper now **syncs `extras.role` to `"conclusion"`** when core
auto-assigns the first premise as conclusion, regardless of the
caller-requested role. The helper's contract becomes: "the first
premise of a brand-new argument is always conclusion, both at the
engine slot AND in `extras.role`." Subsequent premises honor the
caller's intent — the auto-conclusion rule fires only when no
conclusion exists.

## Consumer migration

Route handlers / UI flows in `proposit-server` (and any future
mobile authoring code) that call `mutateUpdatePremiseRole`:

- **Delete defensive demote-then-promote two-call patterns** of the
  shape `mutateUpdatePremiseRole(currentConclusion, "supporting"); mutateUpdatePremiseRole(newPremise, "conclusion");`.
  The first call now throws. Replace with the single promote call —
  shared's promote-to-conclusion branch atomically swaps the prior
  conclusion's role to supporting inside the same helper call.
- **Add 409 mapping** for `InvariantViolationError` carrying
  `code: "ARGUMENT_NO_CONCLUSION"` in any route handler that may
  receive a demote-the-current-conclusion request from the client.
  The error envelope template matches existing grammar-violation
  409 responses.

Consumers that only call `mutateCreatePremise` see the change as a
slightly stricter post-condition (`extras.role` is no longer free to
disagree with the engine slot on the first premise) and don't need
to change anything if they were already reading the post-call
premise data from `engine.getPremise(...)`.

## Out of scope

- The api-client wrapper at `src/api-client/ingest-argument.ts` is
  deferred per the initiative spec (§14 item 11). The path is
  reserved but no typed wrapper ships in 0.13.0.
- The runtime `ProcessingFailureSchema` TypeBox value re-export is
  blocked on core shipping it; a future shared minor will land it.
- Server consumer updates (call-site rewrites + 409 mapping) ship in
  `proposit-server` once it bumps its `@proposit/shared` dep range
  to `^0.13.0`. Mobile has no `mutateUpdatePremiseRole` callers yet;
  its dep bump is dep-only.

## Versioning

Pre-1.0 minor bump (`0.12.2` → `0.13.0`). Per shared's pre-1.0
policy, minor bumps may include breaking changes. The two
behavior changes above are technically breaking for any caller that
relied on the pre-E-7 helper behavior (demote-the-conclusion
succeeding silently, or first-premise `extras.role` being free to
disagree with the engine slot). Both pre-E-7 behaviors were
buggy — they violated the role-state-vs-extras invariant the
helper exists to enforce — so consumers that hit the new throw
were already in a region of the call surface that wouldn't have
held under the engine's new invariants either.
