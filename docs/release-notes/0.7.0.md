# Upcoming release notes

Minor release. Drops the `PERMISSIVE_GRAMMAR_CONFIG` bypass in `populateDerivationFromCitations` and `clearDerivationAntecedent`, so the wave-2 derivation antecedent is now built in the canonical formula-buffered shape that the engine's standard grammar produces. Resolves a strict-vs-auto-normalize checksum divergence on cited arguments in `proposit-server`'s publish path. Background: `docs/change-requests/2026-05-09-derivation-formula-buffer.md`.

## Why this is minor (and not patch)

The wave-2 antecedent shape changes at the data layer. Any consumer that reads the raw expression tree under `IMPLIES` to detect citation-based antecedents must now expect a `formula` node sitting between `IMPLIES` and the underlying `OR` (or `variable` for `n=1`). That's a payload-shape change, so per the maintainer's pre-1.0 versioning policy this is a minor bump and consumers should re-pin.

Nothing in the public function signatures changes. `populateDerivationFromCitations`, `clearDerivationAntecedent`, and `mutateCreateDerivationPremise` keep the same arguments and return shape; only what they emit into the changeset's `expressions` arrays differs.

## What was wrong

`populateDerivationFromCitations` and `clearDerivationAntecedent` wrapped their construction logic in a `withGrammarConfig(pm, PERMISSIVE_GRAMMAR_CONFIG, …)` save/restore that swapped the per-premise grammar to `{ enforceFormulaBetweenOperators: false, autoNormalize: false }` while building or tearing down the antecedent. That produced an unbuffered `IMPLIES(OR(c1, …, cn), Q)` shape for `n ≥ 2` — strict-grammar-illegal, but valid at the per-premise structural level (`validateDerivationStructure` accepts both shapes). The wrapper was a wave-2 holdover from when the goal was shape parity with `@proposit/proposit-core`'s `ManagedDerivationPremiseEngine.populateFromCitations`, which carried the same bypass at the time.

The bypass became the root cause of a publish-time false-positive in `proposit-server`. Server's `checkNormalizationNeeded` constructs both a strict engine and an auto-normalize engine from the same stored snapshot. The auto-normalize engine's `wrapInsertFormula` rule inserts the formula buffer; the strict engine keeps the unwrapped shape. The two engines then hash to different `combinedChecksum()` values and the publish path refuses to proceed, falsely flagging drift on rows that were always saved canonically by every other path.

`proposit-core` shipped the parallel fix on its side as `v0.11.2` (drops the `PERMISSIVE_GRAMMAR_CONFIG` wrapper from `ManagedDerivationPremiseEngine.populateFromCitations`); the change here is the matching fix in `@proposit/shared`.

## What changed

`populateDerivationFromCitations` (in `src/engine/mutations/premises.ts`):

- The `withGrammarConfig(pm, PERMISSIVE_GRAMMAR_CONFIG, …)` wrapper around the IMPLIES + OR + citation-var construction is gone. Standard grammar drives the whole sequence.
- For `n ≥ 2`, the engine's `wrapInsertFormula` auto-normalize rule slips a `formula` expression between IMPLIES and OR, producing the canonical `IMPLIES(formula(OR(c1, …, cn)), Q)` shape.
- For `n = 0` and `n = 1` there is no operator-under-operator nesting, so no formula buffer is inserted and the changeset shape is identical to `0.6.3`.

`clearDerivationAntecedent` (same file):

- The `withGrammarConfig(pm, PERMISSIVE_GRAMMAR_CONFIG, …)` wrapper around `removeExpression(IMPLIES, deleteSubtree=false)` is gone — strict grammar handles the IMPLIES removal cleanly because the promoted child is the consequent variable (not an operator).
- The antecedent dispatch grew a `formula` case. The cascade-remove path (`removeExpression(antecedent.id, true)`) handles `formula → OR → citation_var` children in one shot, and citation-variable id collection walks `formula → OR → children`. The `variable` (n=1) and `operator/or` (legacy n≥2) branches stay so `clearDerivationAntecedent` keeps working on snapshots loaded through the back-compat `LOADING_GRAMMAR` shim.

`mutateCreateDerivationPremise` is unchanged — naked-Q has no nested operators, so it never needed the bypass.

The internal `withGrammarConfig` helper and the `PERMISSIVE_GRAMMAR_CONFIG` import are both dropped from `premises.ts`; nothing else in the module used them.

## Back-compat: the `LOADING_GRAMMAR` shim stays

`PropositArgumentEngine.fromServerData` continues to rewrite per-premise expression configs to `LOADING_GRAMMAR` before `rollback`'s `validate()` pass. That shim is independent of the construction path being fixed here and is needed to keep loading any unmigrated `IMPLIES(OR, Q)` rows still in production databases. It can be revisited and dropped once consumers have run their canonicalization migrations.

## Migration impact

- **`proposit-server`** — Once the dependency is bumped to `^0.7.0`, the server can:
    - Drop `LOAD_GRAMMAR`'s `enforceFormulaBetweenOperators: false` relaxation.
    - Drop the `DERIVATION_GRAMMAR` per-premise override loop.
    - Run a one-shot canonicalization migration that calls `repairArgument(GRAMMAR_DENORMALIZED)` on each `(argumentId, argumentVersion)` joined to `claimCitations`. The repair canonicalizes existing shape-A rows into shape-B via `persistNormalizedState`; this script is the canonicalizer, not throwaway.
    - Drop the seed's pre-publish `repairArgument` call — shared now produces shape-B from the start.
- **`proposit-mobile`** — Same fix applies; no source change required beyond the dependency bump.

## Dependency floor

`@proposit/proposit-core` peer and dev floor lifted from `^0.11.0` to `^0.11.2`. Core v0.11.2 is the parallel fix in `ManagedDerivationPremiseEngine.populateFromCitations` and ships the same canonical-shape canonicalization on its side. Lifting the floor avoids a subtle pitfall: a consumer pinned to `proposit-core@0.11.0` or `0.11.1` that also reaches for core's `populateFromCitations` would still produce the unbuffered shape from that side even though shared is now canonical. Pinning to `^0.11.2` keeps both libraries' construction paths in lockstep.

## Tests

- `src/engine/mutations/__tests__/derivation-premises.test.ts` — `populateDerivationFromCitations` two-source test now expects the formula buffer (descends through `formula → OR` to walk citation children, asserts exactly one formula expression in the changeset). Added an explicit `n=2` structural lock test for the formula's parent/child relationships.
- `clearDerivationAntecedent` populated-removal test now asserts an exact `removed.length === 5` (IMPLIES + formula + OR + 2 citation_vars) instead of the previous `≥ 4`.
- `fromServerData with wave-2 derivation premises` — round-trip test renamed and reworked to descend through the formula buffer; smoke test renamed to make the canonical-shape framing explicit; added a back-compat negative-control test that loads a hand-built shape-A snapshot through `fromServerData`'s `LOADING_GRAMMAR` shim; added a strict-load vs. auto-normalize-load `combinedChecksum` identity test that locks the fixed-point claim explicitly (mirrors `proposit-core`'s v0.11.2 regression).
