# v0.15.0 release notes

`v0.15.0` is a minor release that lands the `@proposit/shared` half
of the ingestion-pipeline retry initiative (Pipeline Refinement,
Area 2 — slice S-shared). A new schema sub-entry plus two api-client
methods ship the wire-contract surface that `proposit-server`'s
retry routes consume. Additive only — no peer-dep changes, no
behavior change to existing schemas or api-client methods.

## What's new

- **`@proposit/shared/schemas/api/task-retry`** — new sub-entry
  exporting the retry response schema:
    - `RetryTaskResponse` — the response for both retry routes. Retry
      is a whole-pipeline re-run (the engine has no single-stage
      resume), so both `POST /api/v1/task/[taskId]/retry` and
      `POST /api/v1/task/[taskId]/pipeline/stages/[stageRowId]/retry`
      produce the same artifact: a fresh `argument_create` task whose
      `previousId` points at the failed task. `RetryTaskResponse` is an
      alias of the existing `ArgumentCreateTask` schema — no new wire
      shape, the task model already modeled retry via `previousId`
      lineage.

- **`@proposit/shared/api-client`** — two new methods registered on the
  factory:
    - `apiClient.retryTask(taskId)` — wraps the whole-task retry route.
    - `apiClient.retryStage(taskId, stageRowId)` — wraps the per-stage
      retry route. `stageRowId` is attribution/logging only; execution
      is a whole-task re-run regardless of which stage triggered it.
      Both are path-params-only POSTs (no request body) and surface a
      server-side rejection (e.g. a non-retryable task) as a parsed
      error reply via the standard `parseResponse` path.

## Schema-design notes for consumers

- `RetryTaskResponse` is **narrowed to `ArgumentCreateTask`**, not the
  full `TaskSchema` union — retry targets ingestion pipeline tasks
  only. Rejecting a non-ingestion task id with a typed 4xx is the
  server route's obligation, not a shared runtime guard;
  `Value.Parse(RetryTaskResponse, …)` enforces the
  `type: "argument_create"` discriminant on parse.
- Both routes are **path-params-only POSTs** — there is no request-body
  schema. The api-client methods use the no-body `parseResponse`
  pattern, not `strictFetch`.
- The server's retry route must return the **bare** `ArgumentCreateTask`
  JSON shape (the fresh task) so `parseResponse(RetryTaskResponse)`
  succeeds — a wrapper (`{ task }`) would break the bare-schema parse.

## Peer-dep range

No peer-dep changes. The existing `@proposit/proposit-core` range
(`^1.1.1`) is sufficient — `RetryTaskResponse` reuses the existing
`ArgumentCreateTask` schema and adds no new core surface.

## Consumer migration

None required. The new sub-entry and api-client methods are additive.
`proposit-server` flips its `@proposit/shared` dep to `^0.15.0` when
adopting (Wave-0 → Wave-1 ordering, orchestrator-coordinated).
`proposit-mobile` is read-only for ingestion and does not consume
retry.

## Versioning

Pre-1.0 minor bump (`0.14.0` → `0.15.0`). Per shared's pre-1.0 policy,
minor bumps may include breaking changes; this one does not.
