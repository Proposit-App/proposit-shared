## What this slice does

Adds two TypeBox response schemas + two api-client methods for the two new pipeline-status endpoints landing in `proposit-server` slice 2F. Slice 2F (the server UI page) cannot start until this slice publishes — server's page route imports the schemas + the api-client methods.

The endpoint shapes are defined verbatim in spec §8.1 (`GET /api/v1/task/[taskId]/pipeline`) and §8.2 (`GET /api/v1/task/[taskId]/pipeline/stages/[stageRowId]/payloads`). This briefing references those sections rather than duplicating; trust the spec.

That's the entire shared-side change. No new types beyond what the schemas derive, no engine changes, no migration of existing types.

## Files to modify

### 1. `src/schemas/api/pipeline-status/index.ts` (new) — barrel

Re-exports the schemas + derived TS types from `./schema.ts`.

### 2. `src/schemas/api/pipeline-status/schema.ts` (new) — the response schemas

Two response shapes per spec §8.1 + §8.2:

```ts
// GetPipelineStatusResponseSchema — for GET /api/v1/task/[taskId]/pipeline
// Response is { run, stages } per spec §8.1; when no pipelineRuns row exists,
// run is null and stages is [].
```

**Critical TypeBox patterns to follow** (per `skill-cefailures:typebox`):

- Every field explicit; no `Type.Any()`.
- `Type.Union([Type.Null(), Type.Object({...})])` for `run: null | {...}`.
- `Type.Union([Type.Literal('success'), Type.Literal('null-output'), Type.Literal('aborted'), Type.Null()])` for `outputStatus` — note the explicit `Type.Null()` member; the `null` is a valid state (while pipeline is running).
- `Type.Optional(...)` only when the field is truly optional (absent vs. present), not for nullable-but-always-present.
- ISO8601 timestamps via `Type.String({ format: 'date-time' })` (or whatever the codebase's standard for ISO timestamps is — grep for an existing schema that uses ISO timestamps and mirror).
- Reuse existing types where possible: `TProcessingFailure` is already exported from `src/processing-failure.ts` (re-exported from core 1.1.1+); use the exported TypeBox schema. **Watch out:** if it's only exported as a TS type and not as a TypeBox value, you'll need to either re-derive the TypeBox value (the cleanest path — define `ProcessingFailureSchema` locally and check it matches the type at compile time via `Static<typeof ProcessingFailureSchema> extends TProcessingFailure ? true : false`) or extend the existing re-export to publish the value. Investigate what's currently published and pick the cleanest path.

Token-usage shape (used in both responses): `{ input: number, output: number, reasoning?: number }`. Likely already exists as `TLlmTokenUsage` from `@proposit/proposit-core@1.1+`; check what's re-exported from shared today.

**Find an existing schema-plus-api-client pair to mirror.** Look at `src/schemas/api/` for the most-recent comparable pattern — likely the grammar-violations envelope (slice from Grammar Tiers) or one of the ingest-argument schemas (slice 1E). Match the file layout + naming convention exactly.

### 3. `src/api-client/tasks/pipeline-status.ts` (new) — two api-client methods

Two methods using `strictFetch`:

- `getTaskPipelineImpl(taskId: string): Promise<TGetPipelineStatusResponse>` — `GET /api/v1/task/[taskId]/pipeline`
- `getTaskPipelineStagePayloadsImpl(taskId: string, stageRowId: string): Promise<TGetPipelineStagePayloadsResponse>` — `GET /api/v1/task/[taskId]/pipeline/stages/[stageRowId]/payloads`

Register both in the api-client `factory.ts` `impls` object so consumers can call `apiClient.getTaskPipeline(...)` / `apiClient.getTaskPipelineStagePayloads(...)`.

**Pattern to follow:** look at `src/api-client/` for the most-recent comparable method — likely something added in slice 1F (ingest-argument) or the grammar-violations slice. Match the impl-function shape + factory registration exactly.

`strictFetch` is the wire-safe fetch wrapper from `src/utils/strict-fetch.ts` (or similar). It takes a request schema + response schema and validates both ends. The `Impl` function in the api-client uses it directly.

### 4. Tests — `test/schemas/api/pipeline-status.test.ts` (new)

TypeBox round-trip + invalid-shape rejection. Per `skill-cefailures:typebox`:

- Round-trip a complete valid response payload through `Value.Parse` (or whatever the project's test convention is) and assert it survives.
- Round-trip the empty-state response (`{ run: null, stages: [] }`) and confirm it survives.
- Negative tests: omit a required field → assert validation fails; pass an invalid `outputStatus` value (e.g., `'unknown'`) → assert validation fails.
- Smaller helper schemas (e.g., the per-stage shape) should have their own focused tests too.

Standard verdict cycle from `docs/agents/proposit-shared-reviewer.md` (Green → release ceremony / Yellow → fold P2s before release / Red → fold P1s + re-review).

The reviewer will focus on:

- TypeBox patterns (no `Type.Any`, explicit Union for nullable, correct `Type.Optional` vs `Type.Union([Null, X])` distinction).
- Schema fidelity to spec §8.1 + §8.2 — every field accounted for, every type correct.
- Api-client method shape matches existing factory pattern.
- Test coverage of the schema variants (round-trip both shapes; negative tests on invalid payloads).
- No accidental coupling to `proposit-server` internals (the schemas are wire contracts; they describe the server's response shape but don't import from server).
