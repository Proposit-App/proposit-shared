# `proposit-core` 0.11 upgrade — `@proposit/shared` 0.5.0 design

**Date:** 2026-05-06
**Status:** Design / awaiting human approval
**Audience:** the `@proposit/shared` agent (primary implementer); the `proposit-server` and `proposit-mobile` agents (downstream consumers — coordination obligations laid out in §9)

---

## 1. Goal

Bring `@proposit/shared` from `0.4.0` to `0.5.0`, consuming `@proposit/proposit-core` `^0.11.0` (skipping `^0.10.x`). Two upstream waves are absorbed in one shared bump:

- **v0.10** — source-as-claim unification: `TCoreSource` is gone; the things you cite are now claims with `type: "citation"`.
- **v0.11** — derivation premises: every premise carries `type: "freeform" | "derivation"`, and core ships `ManagedDerivationPremiseEngine` + helpers behind it.

Shared adopts core's data model wholesale (Path A unification) and re-exports the v0.11 derivation surface for downstream callers (Level B exposure — re-exports only, no shared-side mutation envelopes around it).

## 2. Context

The decision shape was settled across three rounds with the orchestrator/server agent before this spec was drafted:

- **Layer 3 rename: full.** Shared's REST and DB-mirror schemas converge on core's data model. No half-renamed intermediate state.
- **Path A: architectural unification.** Shared's `TSource` is dissolved into citation-typed `TClaim` records with URL/IEEE-reference/content-hash fields as claim extras. Server's wave-1 PR migrates the `sources` table accordingly.
- **Level B: derivation re-exports only.** Shared re-exports `ManagedDerivationPremiseEngine`, `validateDerivationStructure`, `TVariableMaterializer`, and the new derivation/legacy error codes. Mutation envelopes for derivation flows wait for server wave 2 to design the actual flows.
- **Premise `type` discriminator: required.** Shared's wire-format `PropositionalPremiseSchema` mirrors core's required `type` field. Server wave 1 backfills `'freeform'` on existing rows during the same migration that recomputes premise checksums.

Two naming rules govern this spec end-to-end:

1. **When a name in shared collides with a name in core, shared yields.** Concrete instance: shared's existing `ClaimSchema.type` (values `"claim" | "conclusion" | "definition" | "criterion"`) collides with core@0.10's new `TCoreClaim.type` discriminator. Resolution: rename shared's existing field to **`kind`**; `type` then carries core's `"normal" | "citation"`.
2. **Citing claim / source claim, never "cited claim".** Core's `CoreClaimCitationSchema` uses `citingClaimId` and `sourceClaimId`; shared's wire and engine surface follows.

## 3. Architecture (post-0.5.0 end state)

1. **Single claim namespace, two types.** All claims live in one library. Each claim has `type: "normal" | "citation"`, mirroring core. Citation claims carry URL / IEEE-reference / content-hash data inline as optional claim extras (the role core's `IEEECitationClaimSchema` plays in core's IEEE extension). `TSource` as a separate entity is gone.

2. **Citation graph as claim-to-claim edges.** `TClaimSource` becomes `TClaimCitation`. Edges have first-class IDs (new in core@0.10) plus `citingClaimVersion` and `sourceClaimVersion` pinning. The schema extends `CoreClaimCitationSchema` with shared-side application fields (`argumentId`, `version`, `createdOn`), following the pattern shared already uses for `ArgumentSchema` over `CoreArgumentSchema`.

3. **`ClaimSchema.type` field collision — rename to `kind`.** See §2 for rationale. Net result: `ClaimSchema.kind` for category, `ClaimSchema.type` for the normal/citation discriminator. The const `ClaimTypes` and schemas `ClaimTypesSchema` / `TClaimTypesSchema` rename in lockstep to `ClaimKinds` / `ClaimKindsSchema` / `TClaimKindsSchema`. Server wave 1 owns the matching DB column rename.

4. **Premise `type` discriminator threading through wire format.** `PropositionalPremiseSchema` (a `Type.Intersect` over `CorePremiseSchema`) inherits required `type: "freeform" | "derivation"` and optional `derivedClaimId` automatically once the upstream core schema includes them. Verification at commit 1: confirm the inheritance is sufficient and shared doesn't need to explicitly re-declare. `ArgumentDiff` and `FullArgument` premise arrays carry the field automatically.

5. **Engine layer simplification.** `PropositArgumentEngine` drops the parallel `domainSources` / `sourcesMap` machinery — citation claims live in `claimsMap` alongside normal claims. `fromServerData` signature shrinks to `(snapshot, claims, claimCitations)`. `TProjectReactiveSnapshot.domainSources` is gone; consumers filter `Object.values(claims)` by `type === "citation"` for citation-only views. **`toCoreClaim` (the `TClaim` → `TCoreClaim` adapter inside `mutableLookup.get`) and the permissive-restore stub both need to thread `type` through.** This happens in two stages: commit 1 hardcodes `type: "normal"` as a default literal (since core@0.11's `TCoreClaim` requires the field but `ClaimSchema` doesn't carry it yet pre-commit-2), and commit 2 widens `toCoreClaim`'s input type and switches to `type: c.type` once `TClaim` actually has the field. The permissive-restore stub stays at `"normal"` default in both stages (citation claims should not be the missing-from-snapshot kind).

6. **Snapshot wire format.** `SourceManagerSnapshotSchema` deleted. `TArgumentEngineSnapshot.sources` field deleted (mirrors core@0.10's removal).

7. **v0.11 derivation surface (Level B re-exports).** Shared exposes a new `engine/derivation.ts` (reachable via the existing `./engine/*` glob in `package.json` exports) re-exporting `ManagedDerivationPremiseEngine`, `validateDerivationStructure`, `TVariableMaterializer`, and the derivation/legacy error-code constants. Mutation envelopes stay agnostic of premise type — wave-2 server design owns derivation-mutation flow shape.

8. **Wire-format validation-code enum sync.** `schemas/review.ts`'s `TCoreValidationCodeSchema` is shared's mirror of core's exhaustive validation-code enum. Source-related codes in there today (`SOURCE_VARIABLE_ASSOCIATION_INVALID_VARIABLE`, `SOURCE_EXPRESSION_ASSOCIATION_INVALID_PREMISE`, `SOURCE_EXPRESSION_ASSOCIATION_INVALID_EXPRESSION`, `SOURCE_ORPHANED`) almost certainly changed in core@0.10's unification; v0.11 adds derivation/citation-graph codes. The enum gets re-synced against core@0.11.0's actual exported codes at commit 1, separately from any error-class re-exports (those are about `Error` subclasses caught by consumer try-blocks; the validation-code enum is about result-shape strings flowing through `validate()`).

**Net public-API breaking surface for downstream consumers:** `TSource` gone, `TClaimSource` → `TClaimCitation`, `TArgumentDiff.sources`/`claimSources` → just `claimCitations` (citations show up via `claims`), `FullArgument.sources` gone, `ClaimSchema.type` → `ClaimSchema.kind`, `ClaimSchema` gains required `type` and optional citation-extra fields, `ClaimTypes`/`ClaimTypesSchema` → `ClaimKinds`/`ClaimKindsSchema`, `ClaimSearchResultSchema.type` → `kind`, `PropositionalPremiseSchema` gains required `type`, `PropositArgumentEngine.fromServerData` signature shrinks, `domainSources` accessors gone, `addClaimSource`/`getSourcesForClaim`/etc. renamed, REST paths under `/source` → `/citation`, `extractSourceTitle` → `extractCitationTitle`, `maxSourcesPerArg` → `maxCitationsPerArg`.

## 5. Data flow

1. **Server `FullArgument` response.** `{ claims, sources, claimSources, ... }` → `{ claims, claimCitations, ... }`. The `claims` array carries both normal and citation-typed records distinguished by `type`. Citation rows that used to live in `sources` now appear in `claims` with `type: "citation"` and their URL/IEEE/contentHash data inlined as claim-extra fields. Server's loader joins one fewer table.

2. **`PropositArgumentEngine.fromServerData`.** Signature shrinks from `(snapshot, claims, domainSources, claimSources)` to `(snapshot, claims, claimCitations)`. The existing `claimsMap` accepts both normal and citation claims (unchanged storage shape). The old `sourcesMap` and `claimSourcesMap[claimId] = TClaimSource[]` machinery collapses into `claimCitationsMap[citingClaimId] = TClaimCitation[]`. Permissive-stub logic in `mutableLookup.get` continues to work for citation claims now that `toCoreClaim` threads `type` through.

3. **Client-side "give me only citations" view.** Consumers do `Object.values(claims).filter(c => c.type === "citation")` inline. No shared-side memoized accessor in 0.5.0 — call sites memoize at their own boundary if needed. (May be revisited in a later shared bump if usage patterns warrant it.)

4. **Edit flows for citation-claim metadata.** Editing a citation claim's URL or IEEE-reference fields flows through the same claim-mutation path as editing a normal claim's title/body — server PATCHes `/claims/${id}`, the response carries the updated `TClaim`, the engine calls `setClaim`. No special citation-edit pathway needed.

5. **Citation-edge mutations.** New REST surface: `POST /claims/${citingClaimId}/citation/${sourceClaimId}` returns the new `TClaimCitation` (server generates `id`/`checksum`/`citingClaimVersion`/`sourceClaimVersion`). `DELETE /citations/${edgeId}` is the canonical removal path. Engine: `addClaimCitation(cc)` and `removeClaimCitation(edgeId)` (composite-key remover stays as a convenience method).

6. **Premise type discriminator.** Premise creation through shared's `createPremiseWithId` callsites uses core@0.11's typed-bag form: `engine.createPremiseWithId({ type: "freeform", extras, symbol })`. Wire format carries `type` mandatorily. Optimistic reconciliation's premise add/remove diffing is type-agnostic — premises with different `type` values reconcile by ID like any other premise.

7. **Legacy data through the wire.** If a server response contains pre-v0.11 premises (no `type` field) or pre-v0.10 source records, shared's schema validators reject the response at parse time. There is no compatibility shim. Server wave-1 migration is what guarantees this never happens; if it does, the failure mode is "request fails at parse" rather than silent corruption.

## 6. Error handling

Shared stays a thin layer. No wrapper error classes added for v0.10 / v0.11 codes. Two distinct concerns the spec separates explicitly:

- **Validation codes** (`TCoreValidationCodeSchema` enum entries) — string codes flowing through `validate()` results. Sync handled in `schemas/review.ts` per §3.8 / §4.3.
- **Error-class re-exports** — `Error` subclasses thrown by core, caught by consumer try-blocks. Re-exported via `engine/derivation.ts` per §4.8.

The two are different surfaces with different pipelines.

1. **Validation-code-enum re-sync** as covered in §3.8 / §4.3. No wrapper added — shared's enum literal flows through `mappedViolations` in `buildReactiveSnapshot` (engine.ts line ~336) which casts `v.code as TCoreValidationIssue["code"]`. As long as the enum lists the code, the path works.
2. **Existing shared error classes are unchanged.** `NoSessionError`, `PermissionsDeniedError`, `ObjectNotFoundError`, `LimitExceededError`, `RedirectError`, `PublishValidationError`, `ValidationError`, `ChecksumMismatchError`. `ChecksumMismatchError` will fire more often during/right after wave-1 migration as premise checksums shift; expected behavior of the upgrade path.
3. **Citation-graph invariant errors propagate as `InvariantViolationError`.** Core's `ClaimCitationLibrary.add()` rejects cycles and rejects non-citation-typed source claims; those bubble through `engine.validate()` and shared's existing `rollback()` override catches them. The new validation-issue codes (whatever core spells them — verified at commit 1) fold into the existing `mappedViolations` path in `buildReactiveSnapshot` without code changes — that path takes any code string from `invariants.violations[]` and forwards it.
4. **Legacy-data errors at parse time.** TypeBox schema validation fails at the API-client parse boundary before anything reaches the engine. Surfaces as `ValidationError` from shared's existing wrapper, with the TypeBox path indicating the missing field.
5. **Premise type-discriminator misuse at mutation time.** Since shared@0.5.0 only re-exports `ManagedDerivationPremiseEngine` (Level B), there's no shared-side error path to add. Consumer code (server wave 2) handles `DERIVATION_STRUCTURE_INVALID` directly.
6. **Pre-flight evaluation refusal.** Core@0.11's `evaluate`/`checkValidity` refuse on structurally-broken derivation premises (`DERIVATION_STRUCTURE_INVALID_AT_EVALUATION`). Shared's `engine/review/evaluation.ts` flows the result through unchanged — surfaces as a `validationIssues` entry in the reactive snapshot.

**Why this ordering keeps every commit green:**

- Commit 1 leaves the `TSource`/`TClaimSource` schema types intact and the engine's parallel `sourcesMap`/`claimSourcesMap` still typed against them. The constructor signature shrinks because core forced it, but everything downstream still has its types.
- Commit 2 removes the engine's `domainSources` machinery (which was orthogonal to the source-schema rename) and does the `kind` rename (which doesn't touch source-related code). Commit 2 doesn't delete `sources.ts` or rename `TClaimSource` — the engine's `claimSourcesMap` keeps the old type and old name through this commit.
- Commit 3 is the atomic schema-rename commit: the `sources.ts` deletion + `TClaimSource` → `TClaimCitation` rename + engine accessor renames all happen together because they're each other's typecheck dependencies.
- Commit 4 ripples the rename through the REST/API/util/quota surface — none of those depend on the engine internals from commit 3 beyond the now-renamed schema types, which exist after commit 3.
- Commits 5 and 6 are additive (re-exports, docs, version).

## 9. Versioning + downstream coordination

### 9.1 Pre-publish

`pnpm run check` passes. `dist/` regenerates. Release notes / changelog rotated. `package.json` version bumped. Tag `v0.5.0` after merge.

### 9.2 Publish

`pnpm publish --access public` from a clean working tree on `main` after merge.

### 9.3 Server wave 1 (v0.10-equivalent unification)

Depends on shared@0.5.0 being published first. Server-side obligations:

- Bump `@proposit/proposit-core` `^0.9.1` → `^0.11.0` (skipping intermediate).
- Bump `@proposit/shared` `^0.4.x` → `^0.5.0`.
- Knex migration:
    - Drop `sources` table; backfill rows into `claims` with `type='citation'` plus URL/IEEE/contentHash columns or extras.
    - Rename `claimSources` → `claimCitations` with new columns: `id UUID PK`, `citing_claim_id`, `source_claim_id`, `citing_claim_version`, `source_claim_version`, `checksum` (drop `claimId`/`sourceId` after backfill).
    - Rename `claims.type` column to `kind`; add new `type` column (`NOT NULL DEFAULT 'normal'`).
    - Add `propositional_premises.type` (`NOT NULL DEFAULT 'freeform'`) and `derived_claim_id` (`NULL`).
- Recompute checksums on all claims, premises, arguments, **and claim-citations** (the citation rows have their own `checksum` field per §3.2).
- Flip REST routes: `/source` → `/citation`, `/sources/search` → `/citations/search`, **`/api/v1/user/sources` → `/api/v1/user/citations`** (the GET-all endpoint, in addition to the search endpoint).
- Update server-side handlers consuming `domainSources` / `getDomainSource*` accessors. **This is a substantive code change**, not a rename — server's `arg-data-context.tsx`, `derive-source-context.ts`, `reactive-source-list.tsx`, `claim-sources.tsx`, and `use-node-domain.ts` all read `snapshot.domainSources` today. They flip to `Object.values(snapshot.claims).filter(c => c.type === "citation")`.
- **Citation-creation flow becomes two-step.** Today's `addSourceAction` is a single call that creates the source row and attaches it. After 0.5.0, the natural shape is (a) `POST /api/v1/citation/import` (or `/analyze`) creates the citation-typed claim, (b) `POST /claims/${citingClaimId}/citation/${sourceClaimId}` creates the edge. Server may choose to expose a combined wrapper endpoint for UX continuity. Out of scope for shared@0.5.0 — flagging here so server wave 1 plans accordingly.

### 9.4 Server wave 2 (v0.11 derivation surface)

Pure code change. No further DB shape work. Wave 2 introduces actual `ManagedDerivationPremiseEngine` use, `populateFromCitations` flows, and whatever derivation-mutation envelope shape server settles on (which then drives a possible shared@0.6.0 to add Level-C mutation helpers).

### 9.5 Mobile coordination

`proposit-mobile` consumes shared and core. The 0.5.0 bump is **a substantive code change for mobile, not just a version flip**:

- Mobile reads `snapshot.domainSources` and uses `getDomainSource*` accessors today — those are gone in 0.5.0. Mobile flips to `Object.values(snapshot.claims).filter(c => c.type === "citation")` at every call site.
- Public type names imported from `@proposit/shared` change: `TUserSourcesResponse` → `TUserCitationsResponse`, `TSourceWithContext` → `TCitationWithContext`, `TSourceUsage` → `TCitationUsage`, `TSource` → gone (citations are claims), `TClaimSource` → `TClaimCitation`.
- UI strings referencing "Sources" → "Citations" (or whatever language mobile's product side prefers — but the data layer's terminology shifts unconditionally).

Mobile bump is a separate per-repo PR. Should follow server wave-1 merge but doesn't have to ship in lockstep — mobile's existing build keeps working on shared@0.4.x until it explicitly flips. Mobile agent should plan a substantive PR, not a one-line dep bump.

### 9.6 Risk notes

- Once shared@0.5.0 is published, server is on the clock — any in-flight server PR using shared@0.4.x becomes increasingly painful to rebase. Wave 1 should land within ~1 week of shared@0.5.0 publish. Worth socializing this with the user as a soft deadline.
- The shared publish itself is irreversible (npm cannot unpublish published versions after 72h). Final pre-publish review on this design + the implementation plan is the gate.
- Server's migration touches every claim, premise, claim-citation, and argument row. Worth running it in a staging environment first against a recent prod snapshot to confirm checksum recompute timing is acceptable.
